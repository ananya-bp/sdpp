# Phase 1 — Completion Status

Project: AI-Enhanced University Document Issuance, Tracking and Administrative Analytics Portal
(SDP, Course 20ECSW401, Team 27). Checkpoint date: 20 Sep 2026.

## 1. Phase Goal

Set up the project foundation: project structure, Next.js frontend, FastAPI backend, PostgreSQL,
initial database schema, backend configuration, `.env.example`, and a working frontend-to-backend
connection. Expected output: a running project with the backend connected to PostgreSQL.

## 2. What Was Completed

* Monorepo structure (`backend/`, `frontend/`, `docs/`).
* FastAPI backend with settings loaded from `backend/.env`, CORS for the frontend origin, and a
  per-request database session.
* PostgreSQL schema (6 tables) created through an Alembic migration; SQLAlchemy 2 models.
* Idempotent seed script for the 4 document types.
* Three API endpoints (two health checks and the document-type list).
* Next.js status page that calls the backend from the browser and shows API status, database
  status, and the document types read from PostgreSQL, with a Re-check button and an error state.
* 12 automated backend tests (pytest) against the real database.
* README with setup and run instructions; `docs/PROJECT_CONTEXT.md` recording scope, boundaries and
  data rules for later phases.

## 6. Database Changes

Migration `10866ea4850c` ("initial schema"). Database `sdp_portal`. Tested: upgrade, downgrade to
base, upgrade again, and upgrade on a brand-new empty database.

| Table | Columns (summary) | Constraints |
|---|---|---|
| `users` | id, email, password_hash, role, is_active, created_at | unique email; role in (`student`,`admin`) |
| `students` | id, user_id (nullable), usn, full_name, department, semester, cgpa, backlog_count, fee_status, created_at | unique usn, unique user_id; cgpa 0–10; semester 1–8; backlog_count ≥ 0 |
| `document_types` | id, code, name, is_active | unique code |
| `applications` | id, student_id, document_type_id, status (default `SUBMITTED`), submitted_at, approved_at (nullable), updated_at | FKs to students and document_types (RESTRICT); indexes on student_id, document_type_id, status |
| `application_status_history` | id, application_id, status, changed_at, changed_by (nullable), note | FK to applications (CASCADE), to users (SET NULL) |
| `transactions` | id, application_id, amount, payment_status (default `PENDING`), transacted_at | FK to applications (RESTRICT); amount ≥ 0 |

Seed data (via `python -m app.db.seed`): `TRANSCRIPT`, `MIGRATION_CERTIFICATE`,
`DUPLICATE_GRADE_CARD`, `PROVISIONAL_DEGREE_CERTIFICATE`. No student, user or application rows are
seeded. No fees are seeded.

## 11. Important Decisions

1. **Stack:** Next.js (JavaScript, App Router, no Tailwind), FastAPI, PostgreSQL, SQLAlchemy 2 +
   Alembic (psycopg 3 driver). Docker is not used.
2. **Payment is in the workflow** (Eligibility → Payment → AI/ML) per the project brief, although the
   deck's architecture diagram (slide 13) has no Payment box.
3. **Student records are simulated.** `students.user_id` is nullable so a record can exist before the
   student registers. How a registering student is matched to a record is decided in Phase 2.
4. **Turnaround time (TAT) is derived, not stored:** it will be computed from timestamps, so it can
   never disagree with them. The end point of TAT (approval vs. document generated) is to be fixed
   in Phase 4. The column is named `approved_at` to match the brief.
5. **Application status values** are plain strings; the initial value is `SUBMITTED`. The full list is
   finalised in Phase 2 (no DB enum, so it is easy to change).
6. **`fee_status`** uses provisional values `CLEAR` / `DUE`, to be finalised with the eligibility
   rules in Phase 3. **Attendance** was left out because it is not established as required.
7. **Seeded document types** are the four named in the brief. The deck says "duplicate mark cards"
   and also lists a "red card" for the existing KLE Tech system; "Red Card" is not seeded because
   its meaning is not defined in the documents.
8. **No fees, no OCR, no ML, no auth logic** in this phase. Out-of-scope items (blockchain, SHA-256,
   QR, extra LLM features, biometrics) remain excluded.
9. **Secrets:** only `.env.example` files with placeholders are committed; `.env` is git-ignored.
10. **Versions are pinned** to what was tested: Python packages in `requirements.txt`, Node packages
    in `package.json` and `package-lock.json`.

## 12. Environment / Setup Requirements

* Python 3.11+ (tested 3.12.3), Node.js 20.9+ (tested 22.22.2), PostgreSQL 15+ (tested 16.15).
* A PostgreSQL database `sdp_portal` owned by a user you create (see README step 1).
* `backend/.env` created from `backend/.env.example` with your real password (URL-encoded if it
  has special characters).
* Optional: `frontend/.env.local` if the backend is not at `http://localhost:8000`.

## 13. How to Run This Phase

```bash
# 0. PostgreSQL: create user and database (psql as admin)
#    CREATE USER sdp_user WITH PASSWORD 'choose_a_password';
#    CREATE DATABASE sdp_portal OWNER sdp_user;

# 1. Backend (terminal 1)
cd backend
python -m venv .venv
source .venv/bin/activate            # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env                 # Windows: copy .env.example .env  (then edit DATABASE_URL)
alembic upgrade head
python -m app.db.seed
pytest                               # expect: 12 passed
uvicorn app.main:app --reload --port 8000

# 2. Frontend (terminal 2)
cd frontend
npm install
npm run dev                          # open http://localhost:3000
```

Expected: the page shows three green "OK" cards; `http://localhost:8000/docs` opens the API docs.
